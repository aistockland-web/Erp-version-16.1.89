# 17. GitBook Ask and MCP maintainer workflow

**Audience:** GitBook site administrators, documentation maintainers and MCP integration owners. This is an integration-maintenance guide, not an ERP operator workflow.

## Purpose and authority boundary

Use GitBook Ask to cross-check what the published manual currently says about a Stockland ERP process. It is a documentation-retrieval assistant, not evidence that a screen, permission, calculation or transaction exists in the installed ERP.

For every ERP behavior, the authority order is:

1. The exact Stockland ERP **16.2.18** installer/source and its implemented role and server-side checks.
2. Verified behavior in an authenticated 16.2.18 environment.
3. GitBook's published manual and Ask response as a documentation consistency check.

Do not let an Ask answer override the 16.2.18 implementation, and do not use a GitBook answer as a production acceptance result.

## Six-step workflow for maintaining the manual

1. **Inspect the release source.** Read the exact 16.2.18 installer/source. Identify the real page, displayed controls, server action, role requirement, location restriction and expected result. Keep later branches and development builds out of the 16.2.18 evidence set.
2. **Ask the published GitBook site.** Submit a narrowly scoped question about the same process to the site Ask endpoint or exposed MCP tool. Record the answer and the cited GitBook sources.
3. **Compare the evidence.** Compare the Ask answer with the installer implementation and the permission checks. Correct the manual when it is stale or incomplete; do not change application behavior to fit an unsupported documentation answer.
4. **Capture the real screen.** Capture the exact 16.2.18 frontend at the relevant action and result. Identify whether displayed values are approved training fixtures or genuine production evidence. Mask personal and secret information. A fixture screenshot demonstrates interface layout only; it does not prove live production records or release readiness.
5. **Edit the review draft.** Insert each image beside the exact step it illustrates, with useful alt text and a caption. Keep screenshots distinct from Mermaid diagrams. Preserve the existing change request and its history.
6. **Verify before review or publication.** Re-open the changed page in GitBook, inspect the rendered image at desktop and mobile widths, check all links and step order, and verify the change request diff. Request review only after the page renders correctly. Do not merge or publish without the required explicit approval.

## Site Ask REST endpoint

The GitBook Site Ask API is an authenticated, streaming request:

`POST https://api.gitbook.com/v1/orgs/{organizationId}/sites/{siteId}/ask`

For this Stockland manual:

* Organization ID: `KLSnEb857MJJ3uqq4Ipx`
* Site ID: `site_pIxlq`
* Site URL: [Stockland Ethiopia ERP — User Manual 16.2.18](https://stockland-one-member-plc.gitbook.io/docs-user-manual-16.2.18/)

Use a server-side GitBook personal access token or the authorized OAuth identity. The token must be held in the MCP server's secret store (for example, an environment variable named `GITBOOK_API_TOKEN`). Never paste a token into a chat, manual page, screenshot, issue, source file or repository, and never return it in tool output or logs.

### Request shape

Send the question and the scope in JSON. The default scope is appropriate for a site-wide manual check.

```http
POST /v1/orgs/KLSnEb857MJJ3uqq4Ipx/sites/site_pIxlq/ask
Authorization: Bearer $GITBOOK_API_TOKEN
Content-Type: application/json
Accept: text/event-stream
```

```json
{
  "question": "Explain the Stockland ERP 16.2.18 user creation and branch/warehouse assignment process. Identify the supporting manual sections.",
  "scope": {
    "mode": "default"
  }
}
```

The endpoint returns a server-sent event stream. The calling client must consume the stream until it finishes and return the completed answer and any available source references. Do not treat an incomplete partial event as a completed answer.

## Expose Site Ask as an MCP tool

The MCP server used by the agent must expose a callable tool for Site Ask. A client command such as `codex mcp add gitbook --url https://mcp.gitbook.com/mcp` registers the MCP server with that client; it does not, by itself, guarantee that the Site Ask REST operation is included in the server's advertised tool catalogue.

A suitable tool contract is:

* **Tool name:** `gitbook_site_ask`
* **Required argument:** `question` (string)
* **Optional arguments:** `context` (when supported by the API) and `scope` (default: `{"mode":"default"}`)
* **Server responsibility:** call the Site Ask endpoint with the server-held credential, consume the complete event stream, and return the answer plus source references where available.
* **Security:** enforce the authorized site scope; never accept a caller-supplied bearer token; redact credentials from logs; return a clear permission or configuration error if access is unavailable.

The connected GitBook documentation tools should remain available for reading and editing pages. Exposing Site Ask must not silently broaden page-editing or publication permissions.
