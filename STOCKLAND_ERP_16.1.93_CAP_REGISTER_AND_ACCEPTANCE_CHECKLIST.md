## Status rules

- **OPEN / BLOCKER:** must pass before release or live go-live.
- **OPEN / OWNER ACTION:** requires an authorized Stockland HR, Finance, Owner, or site operator; do not infer or auto-create business data.

- **PASS (LIMITED):** the named static/local test passed only; it does not prove live-site operation.
- **CLOSED:** only permitted when reproducible evidence, reviewer, build identity, and acceptance result are attached to the same release candidate.

## Master acceptance requirement — one end-to-end ERP, not a collection of passing screens

The final objective is one operational Stockland ERP with enterprise-grade control outcomes comparable to those users expect from established products such as Odoo/SAP, adapted to Stockland's own approved SOPs and low-resource WordPress hosting. This is not a claim of exact software equivalence or a request to copy proprietary implementations. The acceptance target is functional completeness, controlled authority, traceable state, exact-once posting, reconciled stock/money, reliable reporting, and a usable responsive interface.

**Single architecture:** one existing WordPress plugin; PHP handlers running inside WordPress; existing MySQL/MariaDB database and 49-table contract; existing same-origin REST route model; present role/capability/location controls; immutable ledger/audit history; current branch/site processes. No parallel plugin, separate Node/Express/PostgreSQL service, scheduled-worker dependency, demo company/data, staging application copy, test routes, or CI fixtures in the installable ZIP. QA scripts and generated evidence may live in the repository's `ci/` folder, never in `stockland-erp-app/`.

**Version identity is a hard gate:** the supplied live screen reports 16.1.94, while this historical branch is 16.1.93 built from a 16.1.92 baseline. Do not upload this candidate to the live system. First recover and verify the actual 16.1.94 baseline; then apply the accepted fixes cumulatively and increment from that version.
